## Purpose and the rule

APG must never be unable to work because a builder uses different software, or has no system at all for some of the data. This amendment makes that a design rule, with three parts:

1. **One intake, many ways in.** Every way of supplying data is designed to feed the same Section 04 intake and its controls. No way in gets its own validation, storage or approval rules.
2. **A core way in for every entity.** Each of the 100 entities in revision 4's register has at least one designed Level 1 way in: an import template, document or email capture, an entry screen, a setup question, or a record APG calculates. None of these needs the builder's software. Every required field in every insight's input contract must also have a viable way in that can be verified; every field the contracts name for a supplied record is checked against its own record kind (see "Field-level coverage"). For 53 of the 100 entities, that way in still has to be built (see the supply plan).
3. **A new way in never changes a rule.** Detection rules and financial figures read stored records, whichever way they arrived. Adding a way in, or a builder switching systems, changes the builder's effort, not an insight's logic. Teaching a rule or figure to use data it does not read today is a different thing: a governed change to that rule, with its own change request and tests.

A builder who uses Procore and Xero, and one who runs everything from Excel and email, are meant to get the same insights from the same verified evidence. The first does less typing.

## Architecture: one data supply system

Section 04 specifies one intake with one set of controls. Stage 1 has it only in parts, all tested on synthetic data and none in production. Paths below are inside the `apg/` package.

- A reference intake (`ingest/`) takes 11 record kinds through delivery decisions, reconciliation, field authority (for the material amounts of six of them) and supplier resolution. It does not yet resolve projects, contracts or other entities, and has no freshness thresholds set.
- A second delivery loop (`fin/intake.py`, reused by `det/intake.py` and `mkt/intake.py`) takes 24 more kinds. It reuses the same mapping and delivery decisions, but cross-record checks are made inside the calculations, not by Section 04 reconciliation. The code records its own finding F-16 as closed, because det and mkt reuse the fin loop; the two loops (reference and fin) are still separate, and nothing open tracks merging them, so that merge is new work this amendment adds.
- Two supplied records are written straight to the store: retention events (`fin/cash_states.py`) and extracted documents (`ingest/documents.py`). The source authority register is not stored at all: it is an object built in code and passed to reconciliation (`source_authority.py`), its approval asserted on the object. (Draft 6 said its rows were written straight to the store; that was wrong.)

So this amendment's first job is to bring every kind under one intake. Then it adds the front ends and a readiness layer. Every way in submits through the same stages and records its channel, the person or system, and the time. All kinds share one intake envelope (the common wrapper every submission carries: who, when, through which channel, for which organisation and project) and the same control checkpoints (the Section 04 stages below); the processing between the checkpoints is specific to each kind of record (a bank line, a defect photo, a contract and a forecast line need different validation), as Section 04 already allows.

## The ways in, by level

There are seven ways in: six ways for people or systems to supply data, and the records APG calculates itself. Level 1 holds five of them (four ways to supply data, plus records APG calculates), and every entity has at least one. Level 2 adds site capture where the data starts on site. Level 3 adds integrations to save effort. Each count is the number of entities whose register row lists that way in, split by its state today. "Partly" means something different for each way in, so each says what it means.

### Level 1: core

**Import templates (a synthetic template exists for 37 entities; 29 have none).** These take bulk data from a file, including a system's own export, such as a Procore, Xero or Jobpac report. A blank template the builder fills by hand is a fallback, not effortless capture.

- The builder maps each file layout once: which column is which field, the units, currency and date format (S04 §18). APG suggests the mapping and the builder confirms it. The mapping is saved and versioned.
- Each row gets one of the five Section 04 outcomes (accepted, accepted with warnings, pending reconciliation, quarantined, rejected), with a reason the builder can act on. A blank is never read as zero.
- Today the code reads CSV files only, and every template is a synthetic layout that must stay marked "draft". The gap is real builder layouts, a mapping screen, Excel and programme files, a way to promote a template once it is checked, and templates for the 29 entities without one.
- Real builder files have several worksheets, inconsistent headers, formulas, merged cells, subtotals and odd date formats. Each file family is supported only once real pilot files prove it; an unsupported layout is shown as unsupported, never half-imported. Programme files (XER, and MS Project XML once a sample confirms the format) keep their activities, relationships and calendars; they are not flattened into a table.
- A template cannot carry a value Section 04 says a person must verify. Quote readings (E35) therefore take document capture as their minimum. The approver and checker columns of the specification, landed-cost and import-check templates (E27, E33, E34) are only asserted by the file today, not governed approvals.

**Document and email capture (partly built for 3 entities: quotes, quote readings and the document record; 20 have nothing).** Claims, payment schedules, quotes, invoices, contracts and certificates arrive as documents, often by email.

- The builder uploads a file or forwards an email. The sender is verified and the organisation is never taken from the address alone (S04 §6). The original message and attachment are kept. Every file is scanned and safely parsed before it is read. Who sent it and whether the document is genuine and authorised are separate questions: the second is settled by verification and the authority register, not by the sender.
- Extraction proposes values. A person with the verifier role confirms or corrects every material value before it counts (S04 §12), and APG stores who confirmed it, when, and what they looked at. Verification can be done in batches (for example a page of extracted invoice values), but each value keeps its own confirmation and provenance; batching never weakens the rule.
- "Partly" here means only the verification control exists, with a stand-in parser for quotes. It is not linked to the intake, and a date a person verifies is kept as text and does not reach the authority logic. Finished capture needs an inbox, the verification screen, the link into the intake and real extraction, which needs the Engine and a vendor (EDR-22) not yet chosen. Without extraction, a person keys every value, so finished document capture waits for the vendor (see release A).

**Entry screens (47 entities; none built).** These cover small, frequent facts: one forecast line, one variation, one delay, one retention event.

- One general form engine, not 47 separate screens: forms are generated from each entity's field definitions, so a new entity needs no new screen code. Each kind of record still gets its own task-shaped layout (the questions, evidence and approval steps of a variation differ from a delay or a forecast line), so the user sees the job they are doing, not a database table. It depends on the field-level schema register, a next step from revision 3, for each entity it serves.
- Values pass the same validation as an imported row. Each carries the signed-in person who entered it, and needs approval where the register requires.
- It never edits a held record. Correcting a quarantined or pending record goes through the review queue, with its roles, distinct approvers and recorded disposition (S04 §9, §13); the entry feature may only open that workflow.

**Setup questions (14 entities, counting the rule settings; 2 partly built: the financial policy and the rule settings exist as versioned policy records, with no builder setup question).** Policies, maps, rates and settings the builder sets once and keeps current. They use the same general entry feature.

- Onboarding asks only what the first insights the builder wants need. Further settings are asked for when an insight that needs them is switched on, so nobody configures everything before seeing a result. Settings that affect financial figures keep their approval.
- The cost-code map is required before any figure that groups by cost code. APG suggests matches and the builder confirms each one. A record whose code is not mapped yet still completes intake: it is held as "pending cost-code mapping" only for the figures that need the code, and listed for the person who owns the mapping.
- The financial policy (E90) holds the settings the M4 figures stop without, such as the status maps (`PO_STATUS_MAP_NOT_CONFIGURED`, for example). The rule settings (N01) hold each detection rule's thresholds and windows, R04B's instruction types and R07's pairs of comparable items, which a person declares, the procurement policy the M6 figures read (home currency, delivery-basis table, freshness per decision, scenario settings) and the specification register every M6 comparison needs (material families, attributes, match rules, unit conversions, approved by the specification owner). Today they are held as versioned policy records, counted as approved only once an audited approval exists; the schema and approval logic are in code, and there is no builder setup question.
- The detection-rule thresholds and windows ship pre-set to defaults you approve, so a builder sees results without tuning them; the builder's approver accepts the defaults at onboarding (PG-DS-AC-05) and may later adjust them within the allowed ranges (S06 §5.1 requires thresholds to be configurable within approved boundaries). Two settings have no sensible default and the builder supplies them when the rule is switched on: R04B's instruction types (the builder's own notice categories) and R07's pairs of comparable items (declared by a person). Defaults are allowed here and not for the M6 supplements because a threshold is a choice of sensitivity, while a quote tier or landed cost is a fact from a real quote. The defaults stay general rather than tied to one state's contract forms, because APG is meant for builders in more than one state and contract forms differ; a builder adjusts them to its own contracts.
- **Severity grading is the exception (the owner, 2026-11-12).** How serious a finding is (its grade) is set by the builder at setup, with no defaults and no suggested levels, because builders' jobs range from a couple of million dollars to a hundred million. For each grade the builder may set a dollar amount, a percentage of the job, or both; with both set, the grade applies as soon as either is reached. Until he has set them, every finding still shows, marked "grading not set up yet", with what to do. How the builder's own setting relates to the existing approval of policies by a second person (F-67, PG-DS-AC-05, S06 §8) is settled in the Section 18 assessment. Today severity bands are dollar amounts only, and the code grades with them whether or not anyone approved them (defect candidate DC-11); the materiality model (`materiality.py`) can measure against contract value, forecast final cost or forecast margin, but no severity grading uses it, so grading by a percentage of the job is new design and new code.
- Every answer is versioned, submitted through the intake, and approved by the right role before it takes effect. "Partly" (the financial policy and the rule settings) means versioned policy records exist, counted as approved only once an audited approval exists, with no builder setup question.

**Records APG calculates (11 entities; 7 built or partly built, 4 not).** Baselines, assessments (calculation runs), scenarios, findings, alerts, deadlines and the readiness record, calculated from stored records by APG and recorded with their calculation run (Section 03). Five more entities list an APG-calculated path but are records a person confirms: retention events, root-cause hypotheses, quality cost, outcomes and prevention opportunities. APG may propose a value for those, but a person records or confirms it through an entry screen and the intake, with its own approval, so the entry screen is their minimum way in. The source registry (E02) is a setup question with a calculated alternative. "Partly" mostly means the code calculates the record but does not store it as its own; the exception is the provenance fields, stored on other records.

### Level 2: site capture

**Phone site capture (14 entities; none built).** Delays, defects with photos, deliveries, work allocation, progress, site conditions and instructions, captured where they happen.

- It is a phone-sized version of the general entry feature: the same field definitions, the same validation, the same intake. The phone is enrolled to the organisation, and the time is checked against the server. Whether capture must work offline is a question for discovery.
- The person, time, place and any photo are kept as evidence, subject to Section 09 §14 (labour data privacy and role permissions, as revision 3 cites it). Each record says how the place was established (entered by the person or taken from the device); the device location is not assumed reliable; on a shared site phone the signed-in user is recorded, not the device; workers can see what was recorded about them, and a disputed record goes through the correction route. The detail is left to the cascade impact assessment.
- Every one of its 14 entities also has a Level 1 way in, so it is never the only way in.
- A Level 1 fallback can supply the same fact, but not always at the time it happened. Where timing matters (a delay, an instruction, a defect), a record entered after the event is marked retrospective, and the readiness record qualifies the insight that uses it. A backdated entry never rewrites a result already shown: the earlier result and the records it used stay on record, and the affected insight is reassessed and labelled.

This is a change from revision 3, which listed phone capture among the required features (its decision 3). It moves to Level 2 because every site fact also has an entry screen or a template, so phone capture adds convenience rather than coverage. The owner chose Level 2 with an early discovery gate (decision 6), which replaces revision 3's decision 3 for phone capture. GPT's review agreed with Level 2, provided site needs are tested early (Gemini's did not discuss phone capture): discovery of site capture, including whether it must work offline, is an early gate, not a late one. If discovery shows that one of the first pilot's insights depends on site facts recorded as they happen, that capture is brought forward into release A.

### Level 3: integrations

**Integrations through AUIF (24 entities; none built).** Recurring feeds from systems such as Procore, Xero, MYOB and Jobpac; for Payapps, whether any feed exists is still to confirm with the vendor.

- Each feed has a source registry entry (S04 §4; revision 2 called it a source profile) and lands in the same intake. The authority register decides which system governs which field.
- They remain proposed until the Section 01 discovery. Each is chosen on four tests: the pilot builders actually use the system, it has a usable API or export, its data quality is good enough, and it saves real manual effort. Popularity alone is not a reason.
- Until then, the same data comes through those systems' export files and the import templates.

## Entity supply plan

Each entity has one minimum way in from Level 1, plus the alternatives that satisfy the same requirement. The plan covers the 100 entities of revision 4's register, which now holds N01, the rule settings. For 47 of the 100 the minimum way in is built or partly built; for 53 it is not. The full plan is `SUPPLY_PLAN.csv`, generated from revision 4's registers by `build_supply_plan.py`; moving from revision 3's registers to revision 4's changed no entity's release or minimum way in.

**How the minimum way in is chosen.** A mechanical rule, so it can be checked:

1. Only Level 1 ways in count: import template, document capture, entry screen, setup question, record APG calculates.
2. A value Section 04 says a person must verify (quote readings) takes document capture. Configuration takes a setup question where the register lists one. An APG record takes "APG calculates" only where the register lists it and no entry screen; where people record the fact, the entry screen is the minimum.
3. Otherwise the most-built way in wins (exists, then partly, then not built). Ties go to the template, then document capture, entry screen, setup, APG calculates.

**How each entity is placed in a release.** From revision 4's input contracts, with ranges such as "E47 to E50" read in full, plus five named lists in the script (M6 inputs, intake needs, the intake's own records, the readiness record's dependencies, values that must be verified). "Release" is used so as not to clash with Section 18's build phases; how the two relate is under "What is not proven".

- **Release A:** what a current rule or M4 figure actually reads; the configuration the contracts name, plus N01; the inputs of the current M6 market figures, read from their contracts (revision 4); what the intake needs before it will use those records (the supplier list, and users and roles, which may come from the Anchor platform); the intake's own records; the readiness record; and the two APG outputs of today's code it depends on (findings and calculation runs).
- **Release B:** what closes a known limit of a current rule or figure, for example claims and certificates for revenue, accruals for actual cost, or the programme for delay cost. Supplying these changes nothing until the rule or figure that would use them is changed, under its own change request. Receivables sit here: the overdue-receivables figure reads no record today.
- **Later:** inputs of insights not built yet, settled after builder discovery, and APG outputs that today's code only partly produces (baselines, scenarios, the productivity baseline, the financial-record status), kept as their own records when their use is designed.
- **Optional:** the five developer entities, outside the locked blueprint.

### Field-level coverage

A way in for an entity does not prove a way in for every field a rule reads. Revision 4's `build_code_reads.py` scans the code path of each rule and figure for the fields of the kinds it names that the path reads (over-inclusive within those kinds, a check by its listed rules and not a proof; added after GPT's check of revision 4 found fields the contract text did not name), and `build_field_coverage.py` writes two files from the contracts, that scan and the register, with no hand-entered rows:

- `FIELD_COVERAGE.csv`, one row per contract row (57): each field a contract names, and each field its code path reads, is checked against its own record kind in the field register, never against all kinds pooled. 170 record-kind fields, in 33 entities; none is missing from its kind. Plain words in a contract (such as "amount") are matched to their named field; the project is checked on each kind the M4 figures read, and credit notes, order amendments and bank lines reach it through a linked record. Items that are not template fields each have a supplier: retention events and their fields (a person, through the release A entry form; today a direct write, with no field definition yet), duplicate and reconciliation states (the intake), invoice lines and carrying components (calculated), quote terms such as payment days (values of a quote term), R04B's instruction types (N01).
- `FIELD_SUPPLY_ROUTES.csv`, one row per field (170) and one per contract row that names configuration, per settings entity, plus one for the severity grading levels (56 rows: N01 29, E90 24, E03, E20, E04; a row groups the keys one contract row names): the field's entity, the entity's ways in and their status, whether the intake specifications mark it material (a proxy for S04 §12 and a lower bound: 33 fields), the verification route of each way in, and today's source authority and verification state.

What it shows today: every field is accepted by a built way in, but only by a synthetic template; document capture accepts none of them into the intake yet (it is partly built, not linked); field authority is resolved for 6 fields, the material amounts of the reference intake; 36 more get the reference intake's record-level duplicate, supplier or link checks, 17 its field validation only, and one (the PM-system copy of the invoice amount) is a second source field authority compares; 110 go through the second delivery loop, which checks no authority; the material fields cannot yet be verified by a person through the intake; and no setting has a builder setup question. So no field yet meets PG-DS-AC-12 (a criterion of this design, approved in principle, not a locked blueprint ID), and the report says per row what release A must add. Its limits: it covers the fields the contracts name and the fields the code scan finds on each path; a field reached in a way the scan does not follow would still be missed, so the contracts are confirmed against each rule's tests when the rules are next changed; it lists authority and verification routes, it does not test them; the field register is an inventory of the synthetic templates, not yet a validated schema register. The entry screens and document capture will be generated from the same field definitions once the schema register exists, and the check then runs for each way in as it is built (PG-DS-AC-12).

## Data readiness

APG will tell the builder, per insight, what data it needs, what is missing, who usually holds it and how to supply it. This is the readiness record (E89), which APG will keep for every insight and project. Everything in this section is designed behaviour, not built.

**What it is built from:** revision 2's per-insight contracts (each insight's gate, completeness, freshness, verification and behaviour below the gate), which revisions 3 and 4 keep in force; revision 4's input contracts for each rule, M4 figure and M6 figure; this supply plan; and the intake's outcomes.

**What it will hold for each insight:**

- Its state, from the insight's own gate: eligible, qualified, blocked or unavailable. An insight is never shown as eligible while an input it needs is missing, unverified or stale.
- Each input, with five steps: capture available, validation available, authority established, reconciliation available, decision-eligible. A value that arrived but is unverified or stale stops at its step.
- For each gap: the entity and field, the period, the reason, kept distinct: missing (nobody supplied it, or no built way in yet), unverified, conflicting with another source, stale, not authoritative, or the underlying record does not exist; only verified, eligible information counts, the likely holder of the information, the action owner who can supply or correct it, and the approver where one is needed. The builder assigns or confirms those roles; the way in is named, saying plainly when it is not built.
- Its scope: each readiness item belongs to a project, the organisation, a supplier, the portfolio or external data. A shared missing setting (a policy, a labour rate, the authority register) is raised once, with the projects it affects, not once per project.

**When it is reassessed:** at setup, after each intake batch or material change of state (not row by row; reassessment is queued and combined for large batches, but prompt), on a schedule, and whenever a record is corrected, quarantined, superseded or revoked (S06 §10, S04 §14).

**How fresh is fresh enough.** Revision 3's freshness table gives the starting defaults. Each insight may set a tighter limit for the inputs it depends on; for example, bank lines 31 days old may be acceptable for a historical figure but not for current cash exposure. Bank transactions (31 days), timesheets (two weeks) and delays, defects and plant hire (monthly) are flagged for review in the pilot. An overall fresh status never hides a stale critical input.

**What the builder will see:**

1. **At onboarding, a data checklist.** The builder says which systems they use. APG shows which data those systems can supply through their export files and a template (integrations come later), and which must come another way, with the way in for each. Where the survey's sources say what a system holds, the checklist says so; where it is Claude's judgement (the register's "likely also" column), it says that, until a sample export confirms it.
2. **A missing-data list.** Each gap shows its factors side by side, not folded into one score (S10 §4): the amount affected, urgency, confidence in that amount, whether the person can act now, and what depends on it. A gap is never called a loss or confirmed leakage (S06 §4), and any amount comes from a traceable calculation or is labelled an estimate (S06 §2 and §7, PG-AI-AC-06).
3. **Nudges that name the period, the field and the fix,** for example: "3 May invoices from Acme Electrical have no cost code. Add the code on each invoice (assigned cost-code owner)." The responsible role is configurable. Each gap has a stable identity (entity, field, period and source), and a lifecycle: open, assigned, awaiting evidence, resolved, suppressed, reopened, superseded. A gap found again updates its existing nudge instead of sending a new one; a suppression window and re-notification rules apply, as S06 §9.1 requires for alerts. A nudge links straight to the way in that fixes it (a form, an upload or the review queue), after sign-in. APG prioritises the gaps worth most, allows bulk correction where it is safe, and never asks for data it already holds.

**Every message tells the builder what to do (decision 13).** The owner's rule of 2026-11-12, for the whole of APG: whenever a rule or figure cannot fully do a check or a figure, it says what is missing, why it matters and what the builder is to do, and nothing is silent or shown as complete when it is not. Revision 4's `NOT_ASSESSED_MESSAGES.csv`, generated by scanning the code, lists the messages the production modules give (580 entries, including the 13 cases DC-1 to DC-13 that give no message today; DC-13 is put to the owner), each with who sees it and what the builder is told to do; it fails if the code gives a message its patterns find and the list does not cover. A scan cannot prove that no message is built another way, so each message is proven by a test when it is built. The readiness record, the missing-data list and the nudges deliver those messages; the defect change request after stage 1 is the first place they are built.

An insight whose input has no built way in is shown at the state its gate gives: qualified where the gap only limits it, blocked or unavailable where the input is needed to run it, and never eligible. For example, R04B finds only instructions that were recorded, so until instruction capture is built its results will be labelled "recorded instructions only" (a designed label; the rule does not produce it today).

## Release A: the first usable release

Release A gives every current detection rule, M4 figure and M6 figure a designed Level 1 way in for every input it reads, with no phone capture and no integration. It holds by construction: release A is defined to contain those inputs, so a check of membership could not fail and is not offered as evidence. The field check above is the real test of the fields; the gap list, `RELEASE_A_COVERAGE.csv`, has one row per contract row:

- 29 of the 57 rows read a record that does not go through the Section 04 reference intake today.
- 29 rows need the rule settings (N01), 23 name financial-policy fields (E90), and 9 need both, as the supply plan counts them (a row needs N01 when it is a detection or M6 rule whose configuration names a setting, so D02, MPD1 and the shared rows count as "-" though they run under a pinned policy; a row needs E90 when it names a policy field). `FIELD_SUPPLY_ROUTES.csv` counts settings rows by the entity a contract's configuration names instead (29 rows name N01, one of them the severity grading levels, and 24 name E90), so the two counts differ by design. `SUPPLY_PLAN.csv`, `RELEASE_A_COVERAGE.csv` and `build_supply_plan.py` are in the pack.
- 47 rows name an input, a record or a setting, whose minimum way in is not fully built. In plain terms: every M4 figure waits on the financial policy setup, and every detection rule and M6 figure waits on the settings. One of the 47, overdue receivables, needs only release B data.
- 2 figures read no records at all today (security carrying cost and overdue receivables), so new data alone cannot change them.

**Release A is not complete until three gates are passed:** the M6 input contracts (written in revision 4) are approved; the intake migration (item 1) has passed as its own milestone; and the field-coverage report passes for release A, now including the setting fields and the retention-event fields (PG-DS-AC-12). Release A is also delivered progressively: the first pilot project gets the data its first chosen insights need, then the forms and document types grow. No builder is asked to populate all 100 entities.

**The minimum release A build:**

1. **One intake for every kind, as its own gated milestone.** Bring the 24 kinds of the second delivery loop under the Section 04 intake: reconciliation, authority and resolution beyond suppliers. This is not neutral for the rules: today they use those 24 kinds whenever the record's own checks pass, so reconciling them changes which records the rules and figures may use. It is a separate technical milestone under its own change request. A regression baseline (a saved copy of today's rule and figure results, to compare against) is taken first; every difference is explained and signed off; nothing in release A relies on the merged intake until it passes; afterwards the rules read the reconciled state, as they already do for the 11 reference kinds. PG-DS-AC-03 governs new ways in, not this migration. The two direct writes (retention events, extracted documents) and the in-code authority register are not part of this migration: they enter the reference intake as new record kinds (items 3 and 4), which do not wait for it.
2. **Import, made real.** CSV and Excel, a mapping screen, and a way to promote a checked template out of "draft" (today's code refuses any other status). Of the 32 templates, 27 can be checked against real files (a builder's, or a data source's for market and FX data). The other 5 (specification requirements, quote tiers, quote terms, landed-cost components, import checks) were written as synthetic supplements because no builder file carries them; with the minimum build, builders would fill them by hand.
3. **The general entry feature, for setup and retention only.** Setup questions and the retention-event form are its first uses, so release A needs the field definitions for those entities and the form generator. The source registry, authority register, cost-code map, users and roles (or the Anchor platform's, if Section 01 discovery finds them there), the financial policy with its status maps, and the detection-rule settings come through it.
4. **Retention events and quote readings.** Retention events are recorded through that form and the intake, replacing today's direct write. Quote readings likewise: today's verification control is linked into the intake. Until real extraction exists, one person keys a reading from the attached quote and a second person with the verifier role confirms it, so no material value counts on one person's word (S04 §12 for extracted values, §18 for manual entry).
5. **The M6 input contracts.** Written in revision 4, so the market figures' inputs are checked like the rest; approved with it.
6. **Readiness for the builder.** The readiness record (with the findings and calculation runs it depends on), the onboarding checklist, the missing-data list and nudges; every message a rule or figure gives when it cannot fully assess tells the builder what to do (decision 13).

**Chosen by the owner (2026-11-12): the middle path.** Gemini said the earlier recommendation (every small fact plus finished document capture) was too much for a first release; GPT kept it as the target but asked for a staged rollout; both then agreed with the middle path:

- **Entry forms only for the facts the first pilot's insights need**, beyond setup and retention, added progressively as more insights are switched on. The five M6 supplements are asked for only when a builder uses the market insights, and APG does not invent default values for them, because they are facts from real quotes. Under the middle path, landed-cost components and import checks (E33, E34) get entry forms; specification requirements, quote tiers and quote terms (E27, E31, E32) come by template or by the person-keyed document upload, since the register lists no entry screen for them.
- **Document upload, not finished document capture:** upload and email intake with person-keyed, second-person-confirmed values, used for quote readings, the three M6 supplements above and as evidence attached to records. Because originals are kept, choosing the middle path moves the document record (E83: the original file and its hash) into release A. The supply plan places entities by the mechanical release rule, so it still lists E83 under "later"; with the owner's choice applied, release A is 45 entities, and later 28. Finished capture with real extraction waits until an extraction vendor is chosen (EDR-22), because without it staff would key every value.

Seven release A facts have no way in other than a file under any option: purchase orders, credit notes, timesheets, bank transactions and deliveries, which usually come from the accounting, payroll or job system's export (Claude's judgement, to confirm with pilot builders), and market observations and FX rates, which are data sources rather than builder records. Their fallback, a template the builder fills by hand, is available in release A. Under the middle path, other release A facts also come by file until their entry form is added. Discovery must confirm, for each file, that the pilot builder can really produce it; where it cannot, the readiness record shows the gap and its fallback.

## Data supply governance and lifecycle

The ways in are only half the system. The other half is knowing, for every value, who supplied it, whether it can be trusted, which version counts, who must fix a problem and which conclusions change when it changes. Most of this the blueprint already requires; this section ties it to the ways in. This section is part of the change request.

- **Who does what.** For each kind of record there is a supplier, a checker, a corrector, an approver and an accountable owner if it stays missing. They start from defaults and are confirmed progressively, as each kind of record comes into use. In the readiness record the likely holder is where the information sits, the action owner is the supplier or corrector, and the approver is the approver. One person can hold several roles; the roles stay distinct in the record (for example, a subcontractor claim entered by an administrator, checked by a contract administrator, approved by a commercial manager).
- **Data from outside the office.** Much of it starts with subcontractors, suppliers and consultants. In this design it reaches APG through the builder, by document, email, template or entry form; no external portal is designed.
- **Corrections, disputes and versions.** What was received, what changed, who changed it, why, and which version each insight used are all kept (S04 §13). A change to a record an insight used marks that insight for reassessment; an earlier conclusion stays explainable from the records it used at the time.
- **Access.** Organisation, legal entity, project and role boundaries hold on every way in (S04 §6, §16). Sharing information between related companies or joint ventures is not defined by the blueprint sections in this pack and could conflict with tenant isolation; it needs its own decision.
- **Failed or incomplete supply.** A partial import, an unreadable document, a stopped feed, an unmatched record, a wrong version or a duplicate batch is shown as exactly that, with counts and reasons, and goes to the review queue (S04 §8, §9, §15; PG-DS-AC-13).
- **The builder's effort.** APG asks for the most valuable gaps first, allows safe bulk correction and never asks again for data it already holds.
- **The evidence trail.** Every conclusion traces back through its calculation and rule version to the verified, reconciled records and to the original documents, files, emails and source records, as they were at the time.

## What a new way in may and may not change

A new way in may change the intake code. It may not change a detection rule or financial figure. Rules and figures read stored records, whichever way they arrived; when two ways in supply the same field, for example invoices from both a Xero feed and a template, the authority register decides which governs, never the most recent arrival (S04 §5, §13). Teaching a rule to use new data is its own change request.

**Proposed acceptance criteria for every way in:**

| Id | Criterion |

## What is not proven, and your decisions

This design shows what to build and in what order. It does not show what it costs. No effort or cost estimate is given, because none can be made honestly before the feature designs and a real builder's files exist.

**Not proven yet:**

- **Real file layouts.** Every template is synthetic, and the code reads CSV only. One real builder's exports may need different mappings, and five M6 templates have no real file to check against at all.
- **Extraction quality.** Document capture has a stand-in parser for quotes only. How much a person must correct is unknown until a vendor is chosen.
- **Site behaviour.** What site staff will record on a phone, and how often, is unknown until discovery.
- **One intake.** Bringing the 24 kinds of the second delivery loop, the two direct writes and the in-code authority register under the Section 04 intake is design work not yet done.
- **Production readiness.** Everything is tested on synthetic data only. Under S04 §20, no production feature code starts before the Section 01 Discovery Exit Report is signed off, and tenant isolation and security (S04 §16) must be proven on every path. In Section 18's build sequence (§8), every release starts after Phase 0 and the Discovery Exit Report; release A's work spans phases 1 to 3 (the intake, authority and identity in phase 1, the financial policy in phase 2, readiness and nudges in phase 3); and no release reaches production use without the phase 4 to 6 evidence.
- **The entry feature's basis.** The general entry screen needs the field-level schema register, which is not built yet.
- **Adoption.** A complete way in can still fail if it takes too long. The pilot measures completion rates, correction effort, time to supply and the share of material inputs still missing.

**Decisions, approved in principle by the owner on 2026-11-12.** Section 18 (§6) says a change request may not be approved formally until its cascade impact assessment is complete, so these approve the direction. The conditions GPT attached are folded into this draft (field-level wording, freshness per insight, distinct evidence states, an early site-capture gate, backdating). The full list, with the reasons, is in the decisions document; the eight below are the ones this design states, numbered in this draft's own order (the decisions document's numbers are cited in brackets elsewhere):

1. **The architecture.** One intake, six ways to supply data in three levels plus the records APG calculates, a Level 1 way in for every entity, and no rule changed by any way in.

3. **The release rule.** Release A is what current insights read and need to run, release B is what lifts their known limits (each with its own rule change), and the rest waits for discovery.
4. **Phone capture.** Level 2, with an early discovery gate, brought forward if a first-pilot insight depends on it.
5. **The acceptance criteria.** PG-DS-AC-01 to 14 (14 added with decision 13).
