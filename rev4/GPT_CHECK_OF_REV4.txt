### M4 actual cost — credits

### R04B, LAB and DEF — project ownership

This is a common omission, not three unrelated guesses.

`fin/snap.py`'s `project_of()` reads `project_ref` for ordinary project-owned records (lines 34–44). `Facts.of_project()` uses that function to decide which records belong to a project (lines 80–90).

The relevant rules call it:

* R04B: `rules_commercial.py`, line 64, for `notice`.

* LAB: `rules_ops.py`, lines 129 and 155, for `timesheet` and `work_output`.

* DEF: `rules_ops.py`, line 219, for `defect`.

The contract rows omit those project fields, and the field report consequently omits them.

The same problem also affects other project-scoped rules:

* R04 — `variation.project_ref`.

* R08 — `plant_hire.project_ref`.

* DLY — `delay_event.project_ref`.

* R01 — `budget_line.project_ref` as used by the detection rule.

* R09 — `ctc_line.project_ref`.

* D02 — the project ownership fields of the detection record kinds it scans.

R04's `variation.project_ref` and R09's `ctc_line.project_ref` happen to appear elsewhere in the field report, but that does not make the corresponding detection contracts complete.

BLOCKING — medium cost. Add a shared project-scope contract or explicitly add these fields to the relevant rule contracts. D02 also needs to identify the actual record kinds it scans, rather than merely saying “held records of the detection kinds”.

### R07

The row should disclose that it does not test whether the quote has actually been issued as of the assessment date.

### 3\. Field-level coverage

PARTLY RESOLVED — BLOCKING REMAINS

The report is well structured, and I verified the generator results. It produces:

* 155 record-kind fields across 33 entities.

* 55 settings rows.

* 210 total rows in `FIELD_SUPPLY_ROUTES.csv`.

The generators reproduce their CSVs when run from the register directory. The field-coverage script reports no gaps between the fields named in the contracts and the corresponding record kinds in `FIELD_REGISTER.csv`.

But there is an important limitation in what that proves.

The generator's own description says it checks the fields named in `RULE_INPUT_CONTRACTS.csv` against the field register. It does not check whether the contracts themselves include every field read by the code. It also explicitly says that fields the contracts do not name are outside that first check.

That is why the missing `credit_note.supplier_ref` and project ownership fields are not caught. The report is internally consistent with the contracts, but the contracts are not yet complete against the code.

BLOCKING — medium cost. Correct the contracts first, then regenerate the coverage report. It must include the omitted fields and their routes.
