### Remaining field-level exception: retention events

There is one disclosed exception that should not be mistaken for a complete field route.

`RULE_INPUT_CONTRACTS.csv` has a separate M4 retention-position row for the `retention_event` record. That row has no entry function, so the scanner skips it. The retention calculation does read the event fields:

* `seq`

* `project_ref`

* `from_state`

* `to_state`

* `amount_cents`

* `evidence_ref`

* `actor`

* `actor_kind`

* `actor_roles`

The code is in `fin/cashview.py` (`build_retention`, including its call to `cash_states.events_of`) and `fin/cash_states.py` (`events_of`, `fold` and `check_event`). In particular, `cash_states.py` line 101 reads `project_ref`.

Those nine fields are listed separately in `FIELD_COVERAGE.csv` as person-entered E77 retention-event fields with no field definition yet. They do not have corresponding rows in `FIELD_SUPPLY_ROUTES.csv`. The entity register also says E77 has no entry screen.

This is not a hidden scanner omission: the pack explicitly identifies the skipped row and the missing record definition. But the fields still do not have the same field-by-field supply-route treatment as the 170 fields in the main report.

SHOULD FIX · small/medium

Recommendation: carry the E77 retention-event field definition and route into the Section 18 cascade assessment. It does not prevent the Section 18 assessment from starting because the gap is explicitly disclosed, rather than falsely counted as covered.

### 4\. DC-13: accurate, but its scope is incomplete

PARTLY · SHOULD FIX · small/medium

The central mechanism is now described correctly:

* `fin/snap.py` `project_of()` returns `None` when it cannot establish one project, including when conflicting versions name different projects.

* `det/gather.py` lines 28–30 pins a record with an unknown project into each project's run.

* `mkt/gather.py` lines 46–48 does the same for purchase orders; lines 58–60 do it for project-owned demand and specification records.

* The rules then filter for records that belong to the particular project. An unknown-project record is therefore dropped without being assessed or listed by those rules.

The pack also correctly identifies the principal reachable case today: conflicting versions naming different projects. It says a blank project reference is rejected by the Stage 1 templates.

The remaining problem is which M6 rules DC-13 names.

The DC-13 defect table and `NOT_ASSESSED_MESSAGES.csv` identify the project-scoped detection rules and MPD1. They do not identify the other project-scoped M6 rules that also use project-specific matching:

* MP02

* MP03

* MP04

* MP05

* MP09

The M6 project rule table in `mkt/rules.py` identifies these as project rules. Their purchase-order or coverage paths match by project reference; an unknown-project purchase order can consequently be dropped without the proposed DC-13 message. MPD1 does not make that purchase-order omission visible: its project-held kinds are material demand and specification requirements, not purchase orders.

So the mechanism is right, but the stated scope of the defect is incomplete. Add those M6 rules to the DC-13 description and its message-list entry before the owner decides whether to accept DC-13. This does not reopen the corrected project-field contracts.
